# 0037. A hosted control plane serves executors that run on the developers' machines

## Status

Proposed

## Context

The control plane today is a program on the machine of the person who runs it, and everything it does depends on that machine being awake. What it is made of, from the code:

- **It has no network surface.** Its dependencies are Ecto, Postgrex, Jason and Oban (`control-plane/mix.exs`). It reads GitHub on a timer (eight cron entries in `control-plane/config/config.exs`) and receives nothing. A GitHub webhook, a dashboard or a login has nowhere to arrive.
- **It runs the executor as its own child process.** `ControlPlane.Jobs.RunWorkload` writes `workload.json` into a run directory, opens a port on `executor run --deliver`, reads the executor's standard output as event lines, and reads `record.json` from the directory when the executor exits. The port is opened with no environment of its own, so the executor inherits the control plane's environment, which is where its GitHub and model tokens and its gate secrets (ADR 0027) come from.
- **A claim is a database update and nothing more.** `Workloads.claim/1` moves a `queued` row to `preparing` in one statement. There is no executor identity, no lease and no heartbeat that anyone reads for liveness, although the executor writes a `Heartbeat` event every 30 seconds (`DEFAULT_HEARTBEAT` in `crates/executor/src/cli.rs`) and the runner stops an executor that is silent for 120 seconds.
- **A lost run is failed, not re-run.** `ControlPlane.Recovery` fails every workload that was in flight when the control plane started, and its comment says a lost workload is not re-run: a person re-approves, or resumes the pull request (ADR 0030). Running it again could do the work twice.
- **The workspace is on the control plane's disk.** The runs directory, the free-disk check before a claim (`ControlPlane.Disk`) and the sweep of old checkouts (`ControlPlane.Workspaces`) all assume the run happens where the control plane is.

Facts about what is kept and where it can be seen, measured on 2026-11-22:

- **The database is 25 MB after four days** (`pg_database_size` of the development database: 260 workloads, 5,076 events, first row 2026-11-18). By table: `oban_jobs` 5.9 MB, `events` 5.6 MB, `workloads` 5.5 MB. Of the events, tool calls and tool results are 3.2 MB of about 3.9 MB, and they are the text of files the agent read and commands it ran. At that rate the database is about 6 MB a day, or 2 GB a year if the work stays as it is, which it will not; it is a measurement, not a forecast.
- **The event stream holds fragments of the repository.** The control plane keeps no checkout, but the tool results in its events quote the files the agent opened. "The hosted part holds no repository code" is true of checkouts and of anything that can push, and not true of the record.
- **Both repositories are public** (`erinversfeldcodes/hephaestium` and `erinversfeldcodes/athenaeum`, read with `gh api repos/...`: visibility `public`). A ticket and a pull request are public (ADR 0003), so whatever the control plane writes to either is published.
- **The control plane already writes agent text onto the ticket.** `Tickets` posts the agent's question (`"A question for you: ..."`, ADR 0020) and `Account` posts the agent's own account of what it found, cleaned of terminal escapes and put in a fenced block. Nothing in either removes a secret. Nothing redacts a secret anywhere today: not in an event, not in the record, not in these comments. A change that makes the executor emit no secret it holds is in progress separately; this decision does not depend on it, and the build of the executor link does (see Consequences).
- **Forge, the owner's earlier system, keeps everything local.** Its dashboard is read-only and reachable only on a private tailnet. On a failed ticket it posts one fixed sentence and keeps the reason on the dashboard's run page, because a repository it works on is public and the agent's notes had carried worktree paths and gaps in the machine's environment (ADR 0077 in the forge repository). A tailnet-only dashboard cannot be reached by GitHub, which is why it does not carry over unchanged.
- **The owner's decisions, 2026-11-22.** The first hosted version is for one person, on the public net behind a login. Others host their own, and one hosting may be shared by a team of several users. It is single tenant with a single configuration for now, with many teams possible later. All development is local, so agents and repository scripts run on the developer's machine. Model keys stay with the executor that uses them, because a personal subscription is not shared. The host is Fly with Neon for the database, and the code host is GitHub now and GitLab later. An agent's question is read on the login-protected dashboard, with a pointer on the ticket. Spend limits are not wanted.

The options:

- Option 1: Leave it as it is: the control plane and the executor on one machine. It is the cheapest, it needs nothing built, and it cannot receive a webhook, stops all intake and settling when the machine sleeps, and has nothing for a second person to use.
- Option 2: Do as Forge does: keep everything local and add a read-only dashboard on a private network. A private network is unreachable by a code host, so webhooks are out, and so is a team sharing one hosting.
- Option 3: Host the control plane and also host the runners, so that checkouts, repository scripts and model keys are on the hosted machine. Nothing is needed from the developer's machine, and the hosted machine then holds a checkout of every repository, runs each repository's gates and the agent's changes to them (the code ADR 0027 says is trusted but not safe to hand secrets to), and holds a model key that a personal subscription does not allow to be shared.
- Option 4: Host the control plane only, and let each developer's executor connect out to it. The hosted part has a public address that a code host can reach and a login in front of what people can see; the code, the scripts and the model keys stay where the developer already works.

## Decision

We will go with Option 4.

**What is hosted and what is local.**

- **Hosted:** the control plane. It holds the database (workloads, events, records, the spend ledger), reads and writes the code host, receives its webhooks, decides which ticket is approved and which workload is next, judges what settles, serves the dashboard and the executor link, and holds the credentials it needs to do so: the code-host App's private key, the webhook secret, the session secret and the database credentials. Which App, and how it signs in to the code host, is decided with the provider boundary.
- **Local:** the executor and `heph`. They hold the checkouts, run bootstrap, gates and agents, hold the model key, the developer's code-host token for the push, and the gate secrets (ADR 0027). A developer's executor is what changes a repository.
- **The hosted part holds no checkout, no model key, no push credential and no gate secret.** What it does hold of the repository is the event stream and the record, which quote files the agent read; that is deliberate, because the record is the evidence the runtime decides from (ADR 0022).

**The executor link.**

- **Outbound only.** The executor opens every connection. Nothing on the developer's machine listens, and no tunnel to it is made. The executor needs the control plane's address and a device token, and nothing else.
- **The device token** is issued after a login: the executor shows a short code, the person approves it in the dashboard while logged in, and the control plane hands the executor a token tied to that person's login and a name for the device. The token lets the executor claim workloads whose approver is that login and send events for the ones it holds, and nothing more. It is stored hashed, shown once, revocable from the dashboard, and kept by the executor under the rules ADR 0027 gives secrets (a file only its owner can read). Its lifetime and rotation are a recommendation, not decided here (see below). A login that leaves the allowlist loses its tokens.
- **The workload and the stream keep their contracts.** The control plane sends the workload (the same document, with the same lenses and rounds, ADR 0035) over the link, and the executor sends the same events, then the record at the end. The control plane still enforces the stream rules itself (ADR 0022), now on a stream that arrives over a network, and a stream that breaks a rule fails the workload as before. The transport (one long-lived connection or repeated requests) is left to the build to choose by what survives a closed laptop lid and a corporate proxy; both carry the same messages.
- **A claim is a lease.** A workload goes to the executor of the person who approved its ticket, which the workload already records (`approval.approved_by`); every workload built for a ticket carries that approval, so its reviews, evaluations and revisions go to the same person's executor. An executor claims a workload by presenting its token; the claim records which executor holds it and a lease that ends 120 seconds after the last event or heartbeat, the silence the runner tolerates today. Every event the executor sends extends the lease. A workload whose lease ends is a lost workload.
- **A lost workload is re-queued only if nothing could have been published.** The executor writes the push and the pull request after the gates and the pre-push reviews, so while the stream shows no delivery the work exists only on a machine that has vanished, and running it again does the work once. The stream has no event that says delivery began, so this needs one (an additive event, sent before the push). Until it exists, and for any workload past it, a lost workload fails as it does now and a person re-approves or resumes the pull request. A workload is re-queued at most twice, so a ticket that crashes every executor does not do so for ever. This narrows what the owner's decision says ("re-queued when an executor is lost") to the cases where it is safe, and it is a point to confirm.
- **While no executor is connected,** everything the control plane does by itself goes on: intake, reading the code host, settling, merging, webhooks, status comments and the dashboard. Every workload waits, a review and an evaluation included, because they are agent runs. The dashboard says that a ticket is waiting for its approver's executor, and by name. A workload does not time out for waiting.

**Login and who may do what.**

- **Login is the code host's own.** A person signs in with a GitHub App's user authorization (the web flow). Only logins on an allowlist the operator sets may sign in. Nothing else about a person is stored: the control plane has sessions and device tokens, and no user table.
- **A person's authority is still their permission on the repository** (ADR 0023): a maintainer is a person with write access, and Hephaestium takes direction only from a maintainer. The allowlist decides who may open the dashboard; it grants no authority over a repository. Anything a person does to a repository through the dashboard is done with that person's own user token, so the code host decides whether they may.
- **Public net, so the unauthenticated surface is small:** the sign-in flow, the executor link's device-token exchange, and the code host's webhook endpoint (authenticated by signature, ADR 0039). Everything else needs a session.

**Replying to an agent's question.**

- **The question is shown on the dashboard's run page, and the ticket carries a fixed sentence that says one is waiting and where.** This follows Forge. The ticket carries no question text and no agent account, because the repositories are public. Moving the agent's account of what it found off the ticket as well is recommended on the same ground and is not something the owner has yet decided (see below).
- **The person's reply is posted as that person**: the dashboard comments on the ticket, and applies the ready label again, with the person's own user token. The label is then the person's own approval in the ticket's history, so intake's check that the labeller has write access still means what it says (ADR 0023), and a comment on the ticket is attributed to its author. The control plane never posts a reply, or an approval, under its own identity on a person's behalf.
- **A user token is kept as little as it can be.** Recommended: it lives with the session, encrypted at rest with a key from the environment, and is gone when the session ends; a person whose token has lapsed signs in again. The token's lifetime follows the App's setting for expiring user tokens (to be verified against GitHub's documentation when the App is configured).
- **To verify before building:** that a label applied with a user-to-server token appears in the issue's event list with the person as its actor, because ADR 0023 reads the approval from exactly that event. If it does not, the reply cannot carry the approval and this part must change.

## Consequences

The control plane stops being the machine that does the work, so it can sit where a code host can reach it, run while a laptop sleeps, and be shared. Intake, settling, merging and webhooks continue without any executor. The price is a network between two programs that used to share a pipe, and what that brings:

- **A new public surface with a login in front.** Every route that needs a session is as sound as the session handling, and the route that does not (the webhook) is as sound as its signature check. The hosted part holds the App's private key, which ADR 0033 already calls as sensitive as a deploy key.
- **The record and the database are now on someone else's machines.** Neon holds events that quote repository files, and nothing redacts a secret from them today. The executor link must not be built until the executor emits no secret it holds, because the executor's output is the only place a secret can be removed before it leaves the developer's machine. For a repository that is not public, hosting these fragments with a third party is a decision for the person who hosts, and this ADR does not make it.
- **The control plane no longer reads the code host through the signed-in `gh` of the machine it runs on.** ADR 0023 says the control plane holds no GitHub token because it reads through `gh`; a hosted control plane has no developer's `gh` login, so it holds an App's key and mints short-lived installation tokens, as ADR 0033 already has it do for the review App. This refines that sentence of ADR 0023. Intake still builds a workload by running `heph workload`, which reads through `gh`, so the hosted release carries `heph` and a `gh` that is given the installation token, until the provider boundary replaces them.
- **Housekeeping that assumed one machine moves.** The free-disk check, the runs directory and the sweep of old checkouts belong to the machine that has the checkouts, which is now the executor's. A failed run's workspace is kept for a person to look at (ADR 0035), and that is now on the developer's machine, which the dashboard cannot show.
- **A developer's executor must be on for their work to proceed.** A ticket whose approver has no executor running waits, and a team has no fallback to another person's executor, because their model key is not shared. That is the intended cost of keeping keys local.

Not decided here:

- **Multi-tenancy.** Per-installation settings (the repositories taken in, the review policy, the pinned Athenaeum release), per-approver spend (a spend limit is not wanted; the ledger of ADR 0036 already has what a per-approver view would read), and many teams on one hosting.
- **A shared runner with organisation keys.** Not wanted now; it is Option 3 for a team that wants it, and would need its own decision about what a hosted runner may hold.
- **The device token's lifetime, rotation and number per login.** Recommended: long-lived, revocable from the dashboard, no automatic expiry in the first version.
- **Whether the agent's account of what it found also leaves the ticket.** Recommended yes, on the grounds that decide the question. The failed-ticket reason is the same case.
- **Whether the pointer on the ticket carries a link.** Forge's carries none because its dashboard's hostname was a private tailnet name. A login-protected public address leaks only an address that is public anyway, so a link is recommended.
- **What happens to a queued workload whose ticket is edited, or whose approval is withdrawn, while it waits for an executor.** The workload holds the ticket as it was approved, so an edit cannot reach the agent (the executor does not read the ticket again), but a workload that has waited days is a stale approval. Recommended: an approval voided before the claim cancels the workload, using the same rule as intake.
- **Which GitHub identity the control plane's own writes use** (labels, status comments, merge, check rerun): the review App is kept to approvals (ADR 0033), so a second App, or the login App, is needed. Recommended: one App for sign-in, reads and the control plane's writes, and the review App kept apart.
- **Retention of events and records,** and whether the executor should send tool results at all for a repository that is not public.
- **The executor link's transport, the HTTP library, and whether the hosting is one Fly machine or more.** The control plane assumes one node today. Fly and Neon behaviour not stated here (Neon's pooler and Oban's notifier, scale-to-zero timing, the Fly region) is to be verified when the packaging is built.
